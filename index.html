Detecting Suspicious PowerShell Execution with Sigma

PowerShell is on every Windows host, trusted by administrators and heavily used by attackers (ATT&CK T1059.001). A rule that fires whenever it runs buries analysts in noise, and one that is too narrow misses obfuscation. Good detection sits between the two.

Telemetry you need

  • Process creation with command lines: Sysmon Event ID 1, or Windows Security Event ID 4688 with command-line auditing enabled.
  • Script block content: PowerShell Event ID 4104 for rules that inspect what actually ran.
  • Context: parent process, user and host, to separate administration from attacker behavior.

Approach

I write detections in Sigma so the logic stays portable, then convert to each SIEM with sigma-cli. For PowerShell I think in three layers: command-line flags, script block content, and context such as unusual parents and accounts.

Example: encoded PowerShell

title: Suspicious Encoded PowerShell Command Line
status: experimental
logsource:
  category: process_creation
  product: windows
detection:
  selection_img:
    Image|endswith:
      - '\powershell.exe'
      - '\pwsh.exe'
  selection_flags:
    CommandLine|contains:
      - ' -enc '
      - ' -EncodedCommand '
      - ' -ec '
  condition: selection_img and selection_flags
falsepositives:
  - Legitimate administration scripts
  - Software deployment tools
level: medium
tags:
  - attack.execution
  - attack.t1059.001

Tuning

Administration and deployment tools also use encoded commands. Expect to exclude known parent processes, service accounts and management hosts before using this in production, and revisit those exclusions regularly.

Limitations

  • Attackers can rename the binary or use other abbreviations of the flag, so this is one layer, not full coverage.
  • Obfuscation inside the script needs script block logging to catch.
  • Without command-line auditing the rule has nothing to match, so verify your telemetry before trusting a silent rule.
